## 0.1 部署边界（2026-10-28 用户新需求，覆盖本文原有"云上行"设想）

> **整套系统以本地化部署为主，不进行云端部署；系统必须支持多场地，每个场地下有多台中继与多个节点。**

管理层级由此固定为四级（同日追问后确认："场地下面既有多个物理位置，也可能有多台同位置机器"），与数据模型一一对应（见 `target-stack-landing.md` §5）：

```text
场地 Site ──┬── 中继 Relay（物理位置：起点塔/看台/计时区…，可多个）
            │        └── 接入机 Gateway（一台跑 serve.mjs 的机器，同一位置可多台）
            │                  └── 节点 Node（一块 C5 扫频板，能力由声明决定）
            └── 场地级配置：保留天数 / 时区 / 告警默认值 / 当前布局

部署形态（已定案）：每场地一套本地实例（后端 + 一个 SQLite，只拨本场地的接入机）
                  + 一台局域网只读汇聚实例（定时拉各场地的摘要与事件，必须显示滞后）
```

对拓扑的四条直接影响：

1. **"多场地"= 多组本地实例，不是新增一层云。** 一个场地内多台 `gateway` 是本次需求的核心增量；跨场地由"各自一套实例 + 只读汇聚"承载（`target-stack-landing.md` §7.9–7.11），不是本文的接入方式问题。
2. **原 F3「Pi→云上行钩子」取消。** 跨机器的通道只有三种：**场地内局域网 WS**（实时）、**汇聚实例只读拉取**（滞后、摘要级）、**本地归档包导出/导入**（完整搬家）。任何"设备或网关直连云"不再列入阶段表（§6）。
3. **`AccessSource` 必须带 `site_id` + `relay_id` + `gateway_id`**，否则多场地之后"这块板属于哪"无处可查——原 SPA 不受影响（它一次只连一个接入机端点），受影响的是后端 ingest 的扇出与工作台的选择器。
4. **方式①的"规模上限"问题被定案缓解**：单实例只需承载"一个场地内的多位置多接入机"，而不是全场地的板子；跨场地的容量问题转化成"多套实例各跑各的 + 汇聚只存摘要"。原本 R15（单实例承载全部场地）自动降级。

**命名提醒（避免本文后续读错）**：本文 §1–§4 里的"Pi 中继站"指的是**一台跑 `serve.mjs` 的机器**，在新层级里对应 **`gateway`（接入机）**；用户口中的"中继"是**物理位置**，对应新增的 **`relay`**。两者不是一张表——一个位置可以有两台机器，一台机器也只属于一个位置。

一句话：**只有方式一是"接线即有数据"，方式二和三都是固件工程，不是架构选择题。** 软件侧（S1–S9）必须按方式一的语义设计，把②③做成同样的"接入源"而不是另起一套。

**带宽算术**（决定②③能传什么）：115200 8N1 = 11 520 B/s ≈ **11.25 KiB/s** 理论天花板，而单板 USB 实测稳态 **36–37 KiB/s**（真机）。换算成帧：

- `FULL` 模式 METRICS 帧（8 频道）= 10 + 34 + 8×26 = **252 B** → UART 上限约 **45 帧/秒**（还要扣 TELEMETRY 69 B、文本行与命令往返）。
- `RSSI/SNR` 模式 LEVELS 帧（8 频道）= 10 + 32 + 8×4 = **74 B** → UART 上限约 **150 帧/秒**，可用。
- RAWIQ 单快照 16380×4 B ≈ 65 KB → UART 需 **≥5.7 s**，实际已直接禁用。

**由此得出一条架构规则（2026-10-29 按 F1 实测放宽，但口径不放松）**：非 USB 接入的节点必须降级为低带宽语义——`rawiq` 一律 `unsupported`（UART 上至今直接禁用，②a 没改这条）；`spectrum` 在②a 下是**有界能力**（bins ≤ 512、转速被 `uart_stream_cap()` 反推），所以能力声明必须带**上限字段**（`max_bins`/`paced_rotation_hz`）而不是布尔值。**把有界能力渲染成无界，与把它渲染成 `unsupported` 同样是伪造**；软件侧不得用插值、复制上一帧或降采样"补"出没有的数据。**[基线推断 + F1 实测]**

## 2. 方式一：USB × N 块 C5 → Pi 中继站

```text
 C5 #1 ──USB(usb_serial_jtag)──┐
 C5 #2 ──USB───────────────────┤  Pi4b /dev/widscan58-<SN>（udev 通配别名，realpath 去重）
 C5 #3 ──USB──(经 hub)─────────┘        │
                                        ▼
                    serve.mjs :8080  接入层（已实测）
                      /api/endpoints   端点表 serial:<path> / node:<id>
                      /serial?ep=<id>  字节透传 WS，**单端点单客户端**（4096 busy/replaced）
                      /node?id=<name>  远程节点主动上报（假节点已实测）
                      /api/mode        scan ↔ rh（停/启 rotorhazard）
                      45 s 无入站即判死（心跳 ping，防 CLOSE_WAIT 僵尸占用端点）
                                        │ 每在用端点一条 WS 客户端
                                        ▼
                    rftrack FastAPI :9000  唯一持有者 → 扇出
                      ├─ /ws/bridge/{ep}  字节透传给任意多个浏览器（原 SPA 零改动）
                      ├─ /ws/live         解析后的当前值/事件
                      └─ SQLite           配置 + 事件 + 摘要
```

- **规模上限的真正约束不是 USB 带宽**（Pi4 的 USB2.0 总线 480 Mbps，10 块板 ×37 KiB/s ≈ 3 Mbit/s，余量两个数量级），而是：① serve.mjs 逐字节 `readFrames` + Node 单线程的 CPU；② Pi 可用内存约 460 MB（RH 与 Node 已在跑）；③ USB 口数量（外接 hub 曾出现 `error -71` 枚举失败，真机教训）；④ udev 别名唯一性。**[已由真机实测 + 根据源码推断]** 板数上限**需要实机验证**。
- 已知副作用（必须写进运维文档）：同插两块以上时裸别名 `widscan58` 指向最后枚举的那块；已用 `widscan58-<SN>` 通配别名 + realpath 去重解决。**[已由真机实测]**
- 与 RH 的共存已被真机证明：RH 走 UART（ttyAMA0，8 节点）+ 扫频走 USB，互不抢占。**[已由真机实测]**

**这是唯一不需要改固件的路线，也是 S1–S9 的默认开发/验收拓扑。**

## 3. 方式二：C5 UART → Pi 直连

```text
 C5 GP11(TX) ──┐            现状冲突点
 C5 GP12(RX) ──┼──► Pi PL011 /dev/ttyAMA0 (/dev/serial0)
     GND ──────┘                 ▲
                                 └── RotorHazard 已独占，且 RH 首字节即抢回 radio
```

五个必须逐个拆掉的障碍：

| # | 障碍 | 需要的改动 | 风险 |
|---|---|---|---|
| 1 | 帧只写 USB（`link.c:110`） | `link_frame()` 增加 sink 参数或按 `proto` 路由；UART 侧需要"队列+写任务"（C5 当前注释明说没堆） → 需重算 heap 预算 | 中-高：C5 堆本就紧（保留 128 KiB 采集银行后约 125 KB）**[已由源码确认]** |
| 2 | UART 上 `PROTOCOL MONITOR` 被拒（`commands.c:397`） | 新增显式命令/构建开关（如 `PROTOCOL MONITOR UART`），保持默认行为不变 | 低（纯新增） |
| 3 | UART 一有字节就 `set_proto(PROTO_RH)`（`:677`） | 该行为是 RH 兼容的基石，改动会直接影响现网 RH 用户 → 建议用**新命令进入"UART 扫频"模式**而不是改默认 | **高：影响原功能，须单独分支 + 回归** |
| 4 | 2 s `UART_HOLD_US` 交叉污染（`:399`） | 语义要保留（防抢 RH 的板子），但要给 UART 扫频模式一条明确的持有判定 | 中 |
| 5 | 115200 只有 USB 的 ~30% 带宽 | 提波特率（如 921600，需 USB-UART 芯片支持）**或**接受 LEVELS-only 降级 | 中：波特率与 Pi 端 miniuart 质量相关 |
| 6 | Pi 侧端口所有权 | PL011 归 RH；UART 扫频要么用第二个 UART（ttyS0/miniuart，历史上一动 BT 就闹过 WiFi 问题），要么 **USB-UART 适配器**（物理走 USB，逻辑仍是 UART，逻辑上等价于方式一）——**2026-10-29 裁定：这两条都不走，直接占用 PL011 并在桥接生命周期里停/复 RH**（"用停服务换端口所有权"），见 §3.1/§3.4 | 中，运维复杂度上升 |

**建议（其中"优先推荐适配器"那半句已被 2026-10-29 的裁定推翻，见 §3.1）**：方式二**不进** S1–S9 软件计划，另立固件分支阶段 **F1**，且第一步是"不改代码的可行性实验"：临时把帧路由到 UART + 放开 MONITOR，用逻辑分析仪/回环测真实吞吐与 drops，再决定是否产品化。理由与规范 §2.3 一致：**没有实机证据前不得宣称 UART 接入可用**。

### 3.1 用户裁定（**2026-10-29 覆盖 2026-10-28 的初判**）：方式②走 ②a PL011 直连，②b 适配器取消

2026-10-28 这一度被定为"用 USB-UART 适配器，不去碰 Pi 的 PL011/miniuart"，理由是范围收缩：

- ✅ 不需要在 Pi 上腾端口：`ttyAMA0`(`/dev/serial0`) 继续专供 RH 8 节点，历史上为腾它动 `cmdline.txt`/`config.txt`/`disable-bt` 曾把 WiFi 弄下线过，这条风险在②b 下确实消失。
- ✅ 不碰 miniuart（`ttyS0`）的高波特率可靠性坑。
- ✅ 每台适配器是独立 USB 设备，天然支持"多块 UART 板并列"，不像单个 PL011 只能挂一路。
- ❌ **但固件侧一行都省不掉**：数据从 C5 的 UART0 出去，基线里 `link_frame()` 不写 UART、`PROTOCOL MONITOR` 在 UART 上被拒、UART 一收字节就 `set_proto(PROTO_RH)`（基线行号 `commands.c:397/505-508/677`、`link.c:110`，F1 后见 §1）。**我当时把适配器描述成"不动固件"，那是错的**：适配器换的是"线另一头是谁"，不是"板子愿不愿意在 UART 上发扫频帧"。**这条教训与选②a还是②b无关，保留。**

**改判依据（2026-10-29 用户裁定）**：②a 已经实现、已提交、已部署到 Pi，并且**已经真机跑通一次 UART 扫频**（6.80 KiB/s、558 帧 CRC 全对、断桥自动恢复 RH 8 节点）；②b 至今未实现、硬件未买、零次测量。在"能跑且已验证"对"要买硬件且零测量"面前选了前者。**这个选择的代价是承认并接受下面两条约束，不是免费的**：

1. **UART 扫频与 RotorHazard 计圈在同一台接入机上互斥**——接②a 这个端点就会 `systemctl stop rotorhazard`。场地正在计圈时不能扫，扫的时候计时停。这条必须做成能力位 `stops_rh=true` 并在 UI 里显式确认（见 §5）。
2. **每台接入机只有一块 UART 扫频板**（PL011 只有一路）。要多块 UART 板就得多台接入机，或者回到②b——**而②b 已取消**，所以"单台接入机多块 UART 板"这个拓扑**今天不支持**，别再当成可选项提。

结论：**方式② = F1 固件改造（已完成、已上真机） + ②a PL011 直连（Pi 侧接入形态，已裁定）**。§3 表里"⑥ Pi 侧端口所有权"那一行原本写着两条分支（适配器 / 第二个 UART），现在**定的是"用 PL011 但用停 RH 换端口所有权"**——不腾配置、靠 `--rh-stop-cmd/--rh-start-cmd` 在桥接生命周期里停/复 `rotorhazard`（`serve.mjs:41,219-225,486-504`，Pi 已部署且浏览器确认 `ttyAMA0` 下拉可选）。历史上"动 `cmdline.txt`/`config.txt` 弄挂 WiFi"那条风险**没有被消除，而是被绕开**：这台机器的 `ttyAMA0` 已经在表头上可用，接入时只停服务、不改配置。

> **原本 §3.1/§3.2 的适配器方案已作废**，保留在上面只为记录"为什么改判"和那条"适配器≠免改固件"的教训。**不要再按 §3.2 去买适配器或写 udev 别名。**

### 3.2 ~~适配器接入 Pi 的前置条件~~（**2026-10-29 随②b 一并作废**，保留是为了那条仍然成立的枚举事实）

`serve.mjs` 的 `listSerials()` 只枚举 `/dev/` 下**名字以 `widscan58` 开头**的项（serve.mjs:177-203）。适配器默认枚举成 `/dev/ttyUSB0`，**不在前缀内 → 页面与后端都看不见它**。因此每台适配器需要一条 udev 规则把它挂成 `widscan58-<名字>` 别名：

- 现有规则只匹配 Espressif 原生 USB（`idVendor=="303a", idProduct=="1001"`），适配器（CP210x `10c4:ea60` / FT232 `0403:6001` / CH340 `1a86:7523`）不命中。
- **多个同型号适配器必须按物理端口区分**：CH340/CP2102 普遍没有唯一序列号，按 VID/PID 起别名会全部撞成同一个名字。判据要用 `KERNELS=="<usb-port>"`（物理口路径）而不是设备自身属性。**[需要实机验证]**
- 别名前缀一旦加上，`--serial /dev/widscan58` 的前缀枚举、realpath 去重、busy/4096、心跳全部自动复用，**serve.mjs 零改动**。

## 4. 方式三：GPIO 对接 S3/C5 主控作中继，无线上行或直连云

```text
 子路线 3a（推荐，先做）
 C5 扫频板 ──GPIO(UART 115200, 见 F1)──► 中继 MCU（S3 或另一块 C5）

 子路线 3b（已作废：不做云端部署）
 中继 MCU ──Wi-Fi──TLS──► 云端 ingest（MQTT/HTTPS/WS）
        ✗ 与"本地化部署为主"直接冲突；跨机器改走「场地内局域网 WS」+「本地归档包导出」
```

事实核对：

- **S3 不能当 5.8 GHz 扫频头**（`README.md:74-75` 明说 S3 无 5 GHz 射频，只在 2.4 GHz 跑缩比模拟）。所以方式三里的 S3/C5 主控**只能是中继/宿主**，扫频头仍是那块 C5。**[已由源码确认]**

- Pi 侧的接收端**已经就绪且实测过**：`/node?id=<name>` 接受任意名字的远程节点，id 限 `[A-Za-z0-9_.:-]{1,64}`，同 id 重连发 `replaced`，掉线给页面 close reason "node offline"；已用 Node 假节点跑通端到端。**[已由真机实测]** ——这是方式三最省力的一点：**下游不用动，只缺上游那段中继固件**。
- 中继要做的设计（F2 范围）：
  1. 下行侧（对扫频 C5）：UART 帧读取 + 与 F1 的帧路由对齐；断线检测（静默超阈值 → 上报 node offline）；命令上行（单写者、带请求 ID，避免多浏览器扇出下命令串扰）。
  2. 上行侧（对 Pi）：WS 客户端 + 指数退避重连 + **有界发送缓冲**（Wi-Fi 抖断时按 drop-oldest 计数并上报 dropped 指标，禁止无限堆积把中继 RAM 撑爆）。

## 5. 架构收敛：三种方式在软件侧必须是同一个抽象

后端 ingest 只认"接入源"接口，不认物理介质。（`AccessSource.kind` 是本文档给软件侧定的抽象名，`rftrack/` 尚未创建，代码里还没有这个字段。）

| `AccessSource.kind` | 介质 | 状态 | 该节点 capabilities（示例） |
|---|---|---|---|
| `bridge-ws` | serve.mjs `serial:<path>`，`medium=usb-native` | **已可用** | rssi, snr, spectrum, rawiq, telemetry, scan_rate=full |
| `bridge-ws` | serve.mjs `uart:<path>`（②a Pi PL011 直连，`kind:"uart"`，**②的正式形态**） | **②a 已实现、Pi 已部署；F1 已烧板实测（UART 6.80 KiB/s、558 帧 CRC 全对：442 METRICS / 88 SPECTRUM / 28 TELEMETRY）** | rssi, snr, metrics, spectrum（**有界**：bins ≤ 512、转速被 `uart_stream_cap()` 节流）、telemetry；**rawiq = `unsupported`**（`commands.c:521-525` 仍只走 USB）；**`stops_rh=true`**——桥接会停 RotorHazard，与计圈业务互斥，且每台接入机只此一路 |
| `node-ws` | serve.mjs `node:<id>`（无线中继，方式③3a） | 等 F2 固件（**已决定后置**） | **按基线 LEVELS-only**（中继上游仍是 GPIO/UART，带宽与②同级甚至更低）；F2 若落地要重新按实测声明，不能照抄②a 的数 |
| `local-serial` | Mac 本机 pyserial（开发退化路径） | 已可用 | 同 `bridge-ws` USB |
| `cloud-relay` | 中继/网关绕过场地直连云 | **已作废（用户定：不做云端部署）** | — |

三点说明：

- **②只有 `uart:` 这一种端点形态（②b 已取消，`uart-adapter` 这个 `medium` 不再出现在抽象里）**。已提交的 `serve.mjs` 给出的是 `kind:"uart"` + `uart:<path>` 端点（`serve.mjs:219-225`），并带一条**停/复 RH 的握手**（`bridgeUart()`，`serve.mjs:486-504`）。抽象层因此是 `bridge-ws` 下的两种 `medium`（`usb-native` / `uart-pl011`）+ `node-ws` + `local-serial`，**并且 `uart-pl011` 必须携带能力位 `stops_rh=true`**——"接这个端点会停掉该接入机的计圈"是运营者下单前必须看到的字段，不能藏在实现里，也不能靠 UI 猜。**[2026-10-29 按②a 裁定定稿]**
- **`medium` 决定 capabilities，`kind` 决定传输**。二者必须在同一份声明里，UI 只能按声明渲染。②a 定案后这条有个必须防住的混淆：同一台接入机上会**同时存在** `usb-native`（全能力）和 `uart-pl011`（降级）两种端点，能力位要按**端点的 medium** 声明，不能按"这台机器"给——`uart-pl011` 的 `rawiq` 仍 `unsupported`、`spectrum` 必须带上限。**[规范 §2.3/§5.2]**
- **每个 `AccessSource` 还必须带 `site_id` + `relay_id` + `gateway_id`**（多场地新需求，2026-10-28 定案的四级层级）。判据：`gateway_id` 决定"谁拨的号"，`relay_id` 与 `site_id` 都经 `gateway → relay → site` 推导出来（**不在节点上存 `site_id`**，避免双写不一致，详见 [`target-stack-landing.md` §5](target-stack-landing.md)）；节点身份的全局唯一键是 `(gateway_id, transport_addr)` 而不是裸 `node_id`——同一型号两块板在两个场地都叫 `widscan58-2` 是完全正常的，按名字全局去重会串场地。**[根据 serve.mjs 的端点命名实测推断，需实机验证]**

规则（写进验收标准）：声明缺失的能力一律显示 `unsupported`，**绝不允许软件侧用插值、复制上一帧或降采样"补"出来**。**[规范 §2.3/§5.2]**

规则补充（写进验收标准）：**放开 `spectrum` 之后，声明必须带上限而不是布尔值**。工作区的 F1 实现给出的是"bins ≤ 512、转速被 `uart_stream_cap()` 反推"这种**有界能力**，不是"支持/不支持"。软件侧的 `capabilities_json` 因此要能表达 `spectrum: {max_bins, paced_rotation_hz}` 之类的结构，UI 只能按声明的上限渲染；**把有界能力渲染成无界，与把它渲染成 unsupported 同样是伪造**。**[根据 §3.3 工作区差异，待 F1 提交后定字段名]**

## 8. 当前明确不支持（UI 与文档都不得声称）

- ~~通过 Pi 的 UART 口做扫频~~——**2026-10-29 起这一条不再成立**：②a 已裁定为方式②的正式形态，F1 已提交并烧板、UART 桥实测过 6.80 KiB/s / 558 帧 CRC 全对。但"可用"不等于"无限制"，UI 仍不得声称：UART 上能跑 **RAWIQ**（固件里就排除了，`commands.c:521-525`）、`spectrum` **无上限**（实际 bins ≤ 512、转速被 `uart_stream_cap()` 节流，声明必须带上限）、或**接这个端点不影响 RH**（它会把计时停掉）。
- **同一台接入机上"UART 扫频 + RH 计圈"并行**——②b（USB-UART 适配器）取消后，这条今天没有任何实现路径，页面不得给出"两者同时跑"的选项或暗示。**[已由源码确认：PL011 只有一路]**
- S3 作为 5.8 GHz 扫频节点。**[已由源码确认]**
- 任何节点自主上云（固件无网络客户端）。**[已由源码确认]**

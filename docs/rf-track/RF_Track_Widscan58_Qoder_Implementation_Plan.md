## 1. 项目愿景与范围

RF Track 是在 Widscan58 现有 Web 和设备能力基础上演进的可组合式无线电监测工作台。产品目标包括：

- 在原有 Web 页面中扩展工作台，而不是另建平行前端。
- 让用户从组件库中添加、拖动、缩放、删除和排列监测组件。
- 支持多频道矩阵、单频道详情、RSSI 趋势、频谱、瀑布图/频道活动热图、事件流、目标详情等组件。
- 保留并明确区分局部设置、全局设置、布局设置和后台任务配置。
- 支持工作台布局保存、恢复、另存为、重命名和切换。
- 支持前台视图插件与后台分析插件分离。
- 后台任务可持续接收和分析数据，不依赖对应前台组件是否可见。
- 支持从扫描活动/事件中选择候选对象，查看详情并与其他组件联动。
- 为 ESP32-C5、ESP32-S3、本地 Linux/树莓派网关、多节点接入和未来云端聚合预留接口。
- 本地采集和关键功能优先，不应依赖云端持续在线。
- 为后续多场地、权限、部署、日志、审计和商业化做好架构准备，但第一版不建设复杂插件市场或大规模云平台。

### 1.1 当前范围

当前聚焦于 Widscan58 Web 页面重构与监测工作台、设置、组件、插件、数据适配和探索流程。

不将其他安防项目纳入本项目范围。硬件、固件或 RotorHazard 集成只有在对应阶段明确安排、审计和验收后才实施。

### 1.2 非目标

第一轮改造不承诺：
- 仅靠 RSSI 精确测距、测向或三维定位。
- 在没有频率分辨采样数据时展示真实连续频谱或真实频率—时间瀑布图。
- 在没有 GPS/遥测或可信定位数据时生成真实飞机轨迹。
- 在没有实际硬件验证时宣称某设备能力已经可用。
- 第一版就允许任意第三方代码动态加载或构建插件市场。
- 一次性重写原有 Web、设备固件、DSP 或通信协议。

## 2. 不可违反的工程约束

### 2.1 保护原项目

- 先审计原 Web、USB 数据链路、射频扫描、DSP、RSSI 处理、配置机制和现有功能，再设计集成方案。
- 不得未经批准重写整个前端、替换协议或重构无关代码。
- 不得删除原页面或原功能，除非兼容替代方案已经实现、验证并获用户批准。
- 不得为了让测试通过而隐藏错误、伪造数据、关闭测试或降低原有功能。
- 不得声称某个文件、函数或接口存在，除非从当前仓库确认。
- 新能力优先通过适配器、独立模块和明确接口增量加入。
- 原有页面应在新工作台通过验收前继续可访问。

### 2.2 Git 与工作区安全

- 开始时检查 `git status --short --branch`、`git branch -vv`、`git remote -v` 和近期提交历史。
- 检查未提交修改和未跟踪文件；保护用户工作。
- 禁止擅自运行 `git reset --hard`、`git clean -fd`、强制覆盖文件、强制推送或改写共享历史。
- 不得自动丢弃、覆盖或提交与当前任务无关的用户更改。
- 原始 `main`（或审计确认的原始默认分支）用于保持原版基线。
- 产品开发线建议使用 `develop/rf-monitor-platform`。若当前分支结构不一致，先报告并提出安全方案。
- 功能分支从产品开发线切出，验收后合并回产品开发线。
- 未经用户明确授权，不把完整产品改造合并到原始上游 `main`。
- 回滚优先使用 `git revert <commit>`；涉及数据迁移时，必须提供备份与恢复方案。
- 如果需要推送远程，先确认远程地址、权限和用户意图；默认只在本地操作。

### 2.3 硬件与数据真实性

- 不得把离散频道 RSSI 伪装成连续频谱。
- 只有数据源真实提供频率轴和对应频率点幅度数据时，才可展示真实频谱或频率—时间瀑布图。
- 如果只有离散频道 RSSI，应使用“频道活动热图”“RSSI 时间热图”等准确名称。
- 不得只凭 RSSI 宣称精确距离、方向、坐标或真实飞机轨迹。
- 区分信号活动、疑似目标关联和可信定位轨迹。
- 所有模拟数据必须标记为 `MOCK`、`DEMO` 或等效状态，不能混入真实记录。
- 设备不支持的能力应显示 `unsupported`、`unavailable` 或等效状态，不能伪造。
- 任何固件、DSP 或底层通信修改必须单独说明必要性、风险和回归方案。
- 若后续接入 RotorHazard UART0，GP11/GP12、115200、8N1 等参数必须先从实际代码和硬件确认；若该 UART 承载关键字节流，应独占，禁止调试日志混入，并采用非阻塞、有界队列。没有审计证据时不得直接实施。

### 2.4 性能与可靠性

- UI 拖动、缩放、保存或切换布局不能中断采集、重启设备连接或清空历史。
- 后台任务不得阻塞射频扫描或关键通信。
- 队列必须有界，并明确满载时的背压、丢弃或降级策略。
- 插件异常不得拖垮主采集服务。
- USB、串口和设备数据通过适配层进入统一数据模型。
- 数据源、前台组件、后台分析和布局状态必须解耦。
- 组件销毁时清理订阅、监听器、定时器和资源。
- 对历史数据、事件流、目标列表和缓存设置容量或保留策略。
- 不默认永久保存所有原始数据；记录保留策略和存储上限。
- 对敏感配置采用必要的访问控制和日志脱敏。

## 3. 目标产品界面

### 3.1 页面区域

1. **顶部工具栏**
   - 产品标识和当前工作台名称。
   - 场地/数据源状态。
   - 节点状态入口。
   - 告警入口。
   - 布局管理。
   - 组件库入口。
   - 插件管理入口。
   - 全局设置入口。

2. **左侧组件库**
   - 列出已注册的可用组件。
   - 显示名称、简短描述、能力要求和可用状态。
   - 支持将组件添加到工作区。
   - 不支持或缺少数据能力的组件应明确提示原因。

3. **中央工作区**
   - 支持添加、移动、缩放、删除、复制组件。
   - 支持空状态、加载状态和错误状态。
   - 支持保存、另存为、重命名、切换和恢复布局。
   - 布局操作不得控制后台任务生命周期。

4. **右侧属性面板**
   - 选中组件时显示局部设置。
   - 展示配置来源/继承关系（如全局默认值、布局值、组件实例覆盖值）。
   - 提供保存、取消、恢复默认值和校验错误提示。

5. **全局设置界面**
   - 主题、语言、时区、默认单位。
   - 数据源、节点和连接配置。
   - 默认采集/刷新策略。
   - 告警规则和通知策略。
   - 插件启停和后台任务配置。
   - 日志、诊断、存储和权限等平台级配置。
   - 实际功能必须根据当前项目架构实施，不要为了形式强加不必要的后端服务。

### 3.2 第一批前台组件

| 组件 ID（建议） | 名称 | 主要用途 | 优先级 |
|---|---|---|---|
| `channel-matrix` | 多频道矩阵 | 同时查看多个频道 RSSI、活动状态和更新时间 | P0 |
| `channel-detail` | 单频道详情 | 显示指定频道的当前数据和元信息 | P0 |
| `rssi-trend` | RSSI 趋势 | 显示一段时间的 RSSI 变化 | P0 |
| `signal-events` | 事件信息流 | 显示活动、异常、节点状态和告警事件 | P0 |
| `spectrum-view` | 真实频谱 | 展示真实频率轴和幅度数据 | P1，取决于数据能力 |
| `waterfall-view` | 真实瀑布图 | 展示真实频率—时间—幅度数据 | P1，取决于数据能力 |
| `channel-activity-heatmap` | 频道活动热图 | 只有离散 RSSI 时展示频道—时间活动 | P1 |
| `target-inspector` | 目标详情 | 展示活动/候选目标的证据、时间线和关联观测 | P1 |

### 3.3 工作台交互要求

- 组件从组件库添加到工作区。
- 每个组件实例具有唯一 `instance_id`。
- 同一种组件允许存在多个实例，并拥有独立局部配置。
- 支持拖动、缩放、删除和复制。
- 组件菜单与右侧属性面板共用同一配置逻辑。
- 支持布局保存、另存为、重命名、切换和刷新后恢复。
- 不合法或版本不兼容的布局应安全降级并提供清楚错误提示。
- 删除组件应清理实例状态和数据订阅。
- 缺失插件的布局应保留可恢复信息，不能导致整个工作台崩溃。
- 工作台与原页面共存；在验收完成前不移除原入口。

## 4. 设置系统设计

局部设置和全局设置都是核心需求，必须在早期架构中落实。

### 4.1 配置类别

1. **平台默认值**：内置默认配置。
2. **全局设置**：平台级主题、数据源、节点、默认刷新策略、告警、插件、日志和系统参数。
3. **布局设置**：工作台名称、布局版本、组件位置/尺寸、布局级默认值。
4. **组件实例局部设置**：当前组件的节点、频道、时间范围、阈值、刷新周期、显示方式等。
5. **后台任务配置**：分析规则、任务周期、资源限制、告警关联规则。
6. **运行时状态**：当前选中目标、临时筛选、连接状态等。不得把全部运行时状态塞入布局持久化。

### 4.2 配置优先级

建议优先级：

`平台默认值 < 全局用户设置 < 布局级设置 < 组件实例局部设置`

但权限、安全约束、硬件限制和资源上限不可被下级配置覆盖。

全局设置变化时：
- 更新遵循该全局设置的组件。
- 不静默覆盖用户明确设置的局部值。
- 对需要重启任务或重新连接设备的更改，说明影响并要求确认。
- 普通主题、布局或显示设置不应触发硬件重连。

### 4.3 配置存储原则

- 全局配置与布局数据分开存储。
- 局部配置按组件实例隔离。
- 后台任务配置独立于前台布局。
- 运行时状态使用内存或短期状态存储。
- 优先审计并复用原项目配置机制。
- 不为形式强行增加数据库或独立服务。
- 配置应有版本、默认值、Schema/等效校验和错误处理。
- 配置迁移必须有备份、兼容与回滚方案。
- 保存失败时给出清楚提示，不得假报成功。
- 日志中不得无必要地输出敏感参数。

### 4.4 必须测试的设置行为

- 修改组件 A 的阈值，不影响组件 B。
- 两个同类型组件可拥有不同配置。
- 全局主题变化能同步到遵循全局主题的组件。
- 全局默认刷新周期变化不会静默覆盖明确设置的局部周期。
- 切换布局后恢复对应局部配置。
- 刷新后全局设置和局部设置都能恢复。
- 非法配置不会使整个工作台崩溃。
- 删除组件后清理其配置实例和订阅。
- 局部设置不能绕过权限、硬件安全约束或资源限制。
- 修改普通 UI 设置不会意外重启采集。

## 5. 统一数据模型与适配层

### 5.1 逻辑实体

根据真实代码和协议定义字段，至少评估以下实体：

- `Node`：节点身份、能力、连接状态、固件/协议版本（若可获取）。
- `Channel`：频道标识、频率信息、所属节点。
- `SignalSample`：RSSI、可选 SNR、时间戳、来源节点、数据质量。
- `SpectrumFrame`：真实频率轴、幅度数组、时间戳、来源和采样元信息。
- `SignalEvent`：活动发现、异常、节点离线、告警等事件。
- `CandidateTarget`：候选 ID、关联观测、置信度、证据和复核状态。
- `TrackObservation`：目标时间线中的单次观测。
- `Alert`：规则、等级、事件引用、时间、去重和恢复状态。

### 5.2 数据质量与来源

- 每条观测尽可能携带时间戳、来源节点、数据源和质量状态。
- 区分真实硬件数据、推导数据和模拟数据。
- 不存在的字段应为空或标记不可用，不得随意填造。
- 数据源能力应显式声明，例如是否支持 RSSI、SNR、频谱帧或位置。
- 对时间戳单位、频率单位、RSSI 单位和数据类型建立统一约定，并在代码/文档中说明。
- 防止不同节点 ID、频道 ID 或事件 ID 冲突。
- 适配器负责协议解析、校验、错误转换、断线和恢复处理。

### 5.3 数据源适配器

按审计结果实现或复用：
- 原有 USB/现有数据源适配器。
- 明确标记的模拟数据适配器。
- 为未来本地网关预留的适配接口。

前台组件不能直接操作设备私有接口。不要为了统一模型而随意改变原有设备协议。

### 5.4 频谱真实性

- 只有真实存在频率轴和对应幅度采样的数据，才允许生成 `SpectrumFrame`。
- 离散频道 RSSI 不等于连续频谱。
- 若无真实频谱数据，显示频道活动热图并标注数据类型。
- UI 扫描动画只能用于演示，必须标明 DEMO，不能冒充硬件扫描结果。

## 6. 插件体系

### 6.1 前台视图插件

职责：
- 展示与交互。
- 局部配置。
- 订阅统一数据接口。
- 发出选中频道、事件或目标等交互事件。
- 显示数据缺失、错误和能力不支持状态。

### 6.2 后台分析插件

职责：
- 持续订阅数据或事件。
- 执行分析。
- 输出结构化事件、关联结果或告警。
- 提供运行状态、日志、健康信息和配置。
- 按独立生命周期启动、停止和恢复。

后台插件不能依赖某个 UI 组件是否被显示；前台组件不能直接管理后台进程。

### 6.3 插件元数据与生命周期

至少设计：
- 稳定插件 ID、名称、版本和描述。
- 插件类型、能力声明和依赖。
- 配置 Schema 或等效校验。
- 输入/输出数据类型。
- 启动、停止、健康检查和错误状态。
- 日志、指标、资源限制。
- 版本兼容策略。
- 插件缺失或初始化失败时的降级行为。

第一版采用内置插件注册表、配置启停和受控后台任务。暂不开放任意第三方代码执行或插件市场。

### 6.4 首批后台插件

| 插件 ID | 职责 | 优先级 |
|---|---|---|
| `anomaly-detector` | 检测 RSSI 突变、持续活动等有数据依据的异常 | P1 |
| `interference-correlator` | 关联多频道、多节点异常活动 | P1 |
| `alert-engine` | 规则评估、告警生成、去重、静默和恢复 | P1 |
| `signal-associator` | 将观测关联成候选目标 | P2 |
| `track-engine` | 维护候选目标的活动时间线/可解释轨迹 | P2 |
| `report-engine` | 生成事件摘要和监测报告 | P2 |

### 6.5 后台可靠性要求

- 队列有界，并明确背压/溢出策略。
- 插件启停具有幂等性。
- 任务超时、异常退出和重试可观测。
- 插件崩溃不能拖垮采集主服务。
- 布局保存、隐藏组件或切换工作台不应停止后台任务。
- 任务配置修改要定义热更新与重启规则。
- 服务关闭时清理资源。
- 对 CPU、内存、存储和处理速率设置合理限制。
- 不得在没有审计依据时假设一定需要 Python、Node.js、MQTT、Redis 或大型消息代理；先选择与现有项目兼容的最小方案。

## 7. Signal Explorer：多流探索与目标追踪

### 7.1 交互流程

1. 数据源提供频道、RSSI、频谱帧或其他真实观测。
2. 系统将观测转换为标准事件。
3. 用户在矩阵、趋势、频谱/热图或事件流中选中一个对象。
4. 打开 `target-inspector` 或对应详情面板。
5. 展示来源节点、频道、时间、观测记录、关联事件和数据质量。
6. 其他组件按选中对象联动。
7. 用户查看候选目标时间线、关联依据和置信度。
8. 人工复核状态与算法推测分开保存。

### 7.2 必须区分的三类对象

1. **Signal Activity（信号活动）**：某节点/频道在某时刻观测到活动。
2. **Candidate Target（疑似目标）**：算法基于多个观测建立的候选关联。
3. **Verified Position/Track（可信定位轨迹）**：来自可信 GPS、遥测或其他有效定位源的位置记录。

### 7.3 候选目标字段

至少考虑：
- 稳定 ID。
- 首次和最近观测时间。
- 关联观测引用。
- 来源节点和频道。
- 置信度或证据等级。
- 关联算法及版本。
- 人工复核状态。
- 数据覆盖、未知项和局限说明。

置信度必须由明确算法或规则计算，不能随意生成装饰性数字。

### 7.4 定位能力边界

- RSSI 不是可靠的精确距离测量。
- 多节点 RSSI 关联只能提供候选关系或粗略区域线索，不能直接宣称精确定位。
- 可靠方向估计需要合适的定向天线或多通道测向方案。
- TDoA 等方法需要高精度同步及适合的采样硬件。
- 真实飞机轨迹需要可信定位/遥测来源。
- 没有对应数据时，不显示虚假坐标或轨迹。

- 实现事件/频道/候选目标选择和详情展开。

- 接入真实 USB/现有数据源。

- 评估本地缓存与断网补传扩展点。

- 检查 CPU、内存、延迟、队列、数据丢失和订阅泄漏。
- 完成原功能回归和文档交付。
- 没有实际硬件的测试必须标记为未验证。

时间估算仅供排期，不是质量保证或必须达成的硬期限。

## 10. 测试与验收标准

### 10.1 工作台

- 可添加、移动、缩放、删除和复制组件。
- 布局可以保存、另存为、重命名、切换和恢复。
- 刷新后布局与组件局部配置恢复正确。
- 缺失组件或损坏布局不会使整个页面崩溃。
- 组件销毁后资源和订阅被清理。

### 10.2 设置系统

- 局部设置互相隔离。
- 全局设置能更新遵循它的组件。
- 局部覆盖遵循明确的优先级。
- 布局切换恢复正确配置。
- 非法配置有明确错误提示。
- 普通 UI 设置不会意外重启采集。

### 10.3 数据和组件

- 原 USB/设备数据入口保持兼容。
- 模拟数据与真实数据可区分。
- 断线、重连、无数据和过期数据状态正确。
- 真实频谱只由真实频率分辨数据支持。
- 历史数据和事件流有容量边界。

### 10.4 后台插件

- 插件可查看、启停和配置。
- 运行状态、日志和错误可观察。
- 队列有界。
- 插件崩溃不拖垮主采集服务。
- 切换布局不会停止后台任务。

### 10.5 目标探索

- 选择事件/频道/候选目标后能展开详情。
- 多组件联动正确。
- 关联结果显示来源、证据和不确定性。
- 不会生成无来源的坐标、置信度或真实飞机轨迹。
- 人工复核与算法推测分开记录。

### 10.6 回归和性能

- 原有 Web 页面和功能仍可使用。
- 原有 USB 数据展示、扫描、RSSI 和 DSP 行为没有被意外破坏。
- 测试 40+ 频道和多组件并行。
- 检查长时间运行、事件增长、断线恢复、布局频繁变化。
- 记录实际 CPU、内存、延迟、队列、错误率和数据丢失情况。
- 不得编造性能数据或测试通过结论。
